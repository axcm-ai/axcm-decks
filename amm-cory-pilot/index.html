Why this, why now ›
  • Cut operational overhead: move repeatable AXCM↔AMM grind off people and onto AI agents — not brittle scripts or fixed automations. Agents can read context, decide next steps, use tools, and handle variation the way a person would.
  • Repurpose capacity: free AXCM (and AMM) talent for judgment work instead of status chasing, copy tweaks, and follow-ups.
  • Faster cycle time: agents draft, research, and prep updates in minutes so reviews happen the same day — not after a queue builds up.
  • More consistent delivery: the workflow doesn’t depend on who is in the office or who remembers the checklist.
  • Clearer ROI path: pay for managed agents at a fraction of loaded human time on the same lanes — prove it on one lane first, then expand.
  • You’re first — with the paperwork already in place: AMM already trusts AXCM, and there is an existing BAA (AXCM ↔ AMM). Piloting here means we shape the model together before it goes wide.
How we’d work together ›
  • Assess: Lance reviews with Cory (public website) or Hamilton (AXCM↔AMM workflows).
  • Plan: Lance drafts a short plan for Cory / Duane.
  • Approve: Cory / Duane green-light the plan.
  • Build: AXCM implements — stands up the agent(s), owns setup/changes, and enables Cory’s team to work with them directly under that approval.

AXCM owns setup, implementation, and any changes to AMM Public Web Lead. Cory directs in plain English, approves what publishes, and can work with the agent directly for updates and status.

Idea 2 — Ops lanes (PHI) · AXCM ↔ AMM ›
  • Assessment: AXCM reviews current AXCM↔AMM workflows with Hamilton.
  • Process design: AXCM drafts an agent process document covering lanes, handoffs, and success criteria.
  • Approval: Cory, Duane, and Hamilton review and approve the plan before build.

AMM data stays in AMM’s GCP tenant. Ops agents that handle PHI run against that environment under the existing AXCM ↔ AMM BAA — scoped and approved before anything sensitive is connected.

Idea 3 — Systems (custom apps in AMM GCP) ›

Where AMM is paying per-seat SaaS for workflows AXCM can own end-to-end, we can replace those tools with purpose-built systems — hosted in AMM’s GCP tenant.

  • AXCM proof points: we replaced Bamboo HR and PandaDoc with custom AXCM-built solutions, cutting recurring per-user / per-seat license cost while keeping the workflows we actually use.
  • Same offer for AMM: review the corporate tools AMM rents today; where the math and process fit, design a replacement that matches how the team works.
  • Data residency: custom systems are built and run in AMM’s GCP tenant — AMM data stays with AMM.
  • How we engage: assessment with Hamilton / ops leads → short plan for Cory / Duane / Hamilton → approve → AXCM implements and owns setup and changes.
  • Direct access: designated leads work the new system day to day; AXCM handles build, configuration, and enhancements.

Best fit: HR-style admin, document workflows, internal ops tools, and similar seat-based SaaS — not a clinical product rebuild unless AMM’s tech team invites that scope separately.
