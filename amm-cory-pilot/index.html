Prerequisites and Requirements ›

Before the demo works end to end, these basics need to be in place. Think of it as: Cory talks to the bot → the bot updates the site in GitHub → GitHub puts the site live on Google Cloud.

  • 1. Host the website on Google Cloud (GCP). Put the public marketing site in one place AMM already uses for cloud work, so hosting stays in a single environment — not scattered across old tools.
  • 2. Start from Cory’s current website. Use what’s live today (and any files Cory already has). The bot can open and review the current public site as the starting point.
  • 3. The bot reviews the site and rebuilds it in GitHub. GitHub is simply the shared folder that keeps every page file and a history of changes. The bot recreates the site there so updates are clear, reviewable, and easy to undo.
  • 4. GitHub publishes the site to Google Cloud. When a change is approved, the new version goes from that shared folder out to the live public URL on Google Cloud.
  • 5. Connect the pieces so they talk to each other. One-time setup so the bot, GitHub, and Google Cloud hosting work as one path — Cory briefs in plain English; the bot drafts; people approve; then the live site updates.

People and safety checks before cutover:

  • DNS manager — name the person or team who can change the “where this website points” settings, and who will flip those settings on cutover day.
  • Domain ownership — confirm who currently owns and controls the domain name(s) and can authorize the move (for example assurancemedicationmanagement.com and assurancemm.com).
  • Secure lock (SSL/TLS certificate) — after the move to Google Cloud, the padlock in the browser is usually handled automatically by the hosting; know who watches renewals if anything needs a human.
  • Rollback / backup plan — keep a simple way back: leave the old site running until the new one looks right, keep a copy of today’s pages, and know how to point the domain back if something goes sideways.

Rough costs for the pieces (typical list prices — not an invoice):

  • Google Cloud / Firebase Hosting — often free at brochure-site scale (Google’s free hosting plan covers a normal company website).
  • GitHub — free for a public website folder; paid team features only if you need them later (often about $4+/user/month).
  • WebLead bot (Grok Bot seat) — typically about $100/month on Lance’s stack for the pilot; Cory does not need a separate seat to start.
  • Domain name — typically about $10–20/year to keep assurancemedicationmanagement.com / assurancemm.com registered (DNS cutover is a one-time setup).

Dollar figures are typical public list prices and can change. Lance will confirm exact accounts before anything is billed to AMM.

Idea 3 — Systems (custom apps in AMM GCP) ›

Where AMM is paying per-seat SaaS for workflows AXCM can own end-to-end, we can replace those tools with purpose-built systems — hosted in AMM’s GCP tenant — then put agents on top to do the day-to-day work inside those systems.

  • AXCM proof points: we replaced Bamboo HR and PandaDoc with custom AXCM-built solutions, cutting recurring per-user / per-seat license cost while keeping the workflows we actually use.
  • Same offer for AMM: review the corporate tools AMM rents today; where the math and process fit, design a replacement that matches how the team works.
  • Data residency: custom systems are built and run in AMM’s GCP tenant — AMM data stays with AMM.
  • How we engage: assessment with Hamilton / ops leads → short plan for Cory / Duane / Hamilton → approve → AXCM implements and owns setup and changes.
  • Then agents do the work: once the app exists, named agents operate inside it — Cory and designated leads can converse with those agents for status and requests.

Examples (app + agent)

  • HR / onboarding app (Bamboo-style): agent drafts offer packets, kicks off onboarding checklists, nudges missing forms, and summarizes open tasks for Hamilton.
  • Documents app (PandaDoc-style): agent prepares agreement packets, routes for signature, tracks who hasn’t signed, and reports status to Cory without a license seat for every viewer.
  • Ops intake / ticket board: agent triages requests, fills structured fields, proposes next steps, and updates the board after approval.
  • Internal reporting board: agent pulls the week’s activity, drafts a short brief, and answers “what’s stuck?” in plain English.

Pattern: build the system in AMM’s GCP → attach agents that work the system → humans approve exceptions. Best fit is admin, documents, and internal ops — not a clinical product rebuild unless AMM’s tech team invites that scope separately.
